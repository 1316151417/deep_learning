分词：把文本压成有限符号序列

神经网络不能直接吃“文字意义”，它吃的是一维 token 序列；分词是在词表大小和序列长度之间做权衡。

回到顶部
核心观点

神经网络不能直接吃“文字意义”，它吃的是一维 token 序列；分词是在词表大小和序列长度之间做权衡。

观点

  • 比特序列太长，字节序列短一些，BPE 继续把常见片段合并，让序列更短。
  • token ID 只是符号编号，不要把它当成有大小意义的数字。
  • 分词会影响模型的拼写、计数、多语言表现，以及上下文窗口的使用效率。

定义

  • UTF-8把文本编码成计算机可存储的比特序列的一种标准。
  • 字节8 个比特组成的单位，共有 256 种可能取值。
  • BPEByte Pair Encoding，字节对编码；不断合并常见相邻符号，得到更大的词表和更短的序列。
  • token词元；模型实际处理的最小符号单元，可以是字、词、空格加词、标点或更奇怪的片段。
  • 词表模型允许出现的所有 token 集合。GPT-4 相关分词器约有 10 万个符号。

示例

  • “hello world”在 GPT-4 的 CL100K base 分词器中可被切成两个 token。
  • 大小写、空格数量变化会改变分词结果，所以“Hello world”和“hello world”不一定一样。

训练与推理：预测下一个词元

LLM 训练的核心任务非常朴素：给一段上下文，预测真实数据里接下来的 token，并不断调参数降低错误。

回到顶部
核心观点

LLM 训练的核心任务非常朴素：给一段上下文，预测真实数据里接下来的 token，并不断调参数降低错误。

观点

  • 训练不是写规则，而是通过海量例子调整参数，让输出概率符合数据统计。
  • Transformer 是一个巨大数学函数，输入 token 和固定参数混合后输出下一个 token 的概率分布。
  • 推理时模型不会学习新参数，它只是反复采样 token，把结果接回上下文继续预测。

核心观点

预训练产物是基座模型，它像互联网文本的有损压缩包；它会续写文档，但还不是可靠助手。

观点

  • 基座模型拥有大量知识，但这些知识是模糊、概率性、统计性的回忆。
  • 它会记忆高频或重复出现的文本，也会在未知事实上生成“平行宇宙”。
  • 只靠提示词也能诱导基座模型做任务，但本质仍是续写符合上下文模式的 token。

定义

  • 基座模型只经过预训练、尚未被系统训练成对话助手的模型。
  • 有损压缩参数保留了互联网文本的整体统计印象，但不是逐字可查的数据库。
  • 幻觉模型在缺乏可靠知识时生成看似合理但不真实的内容。
  • 少样本提示在提示词中给几个输入输出例子，让模型在上下文里学会模式。
  • 上下文学习模型在当前上下文中识别模式并临时按模式续写的能力。

示例

  • 问基座模型“2+2 等于几”，它可能只是补全网页式文本，不稳定地回答。
  • 给几个英文到韩语的词对，再写 teacher:，模型可以续写出韩语翻译。
  • 把提示词写成人类和 AI 助手的对话，基座模型会继续扮演助手。

L75接下来我们要讨论几种对这些模型进行所谓后训练的方法。后训练中的这些阶段在计算上会便宜得多：绝大部分的计算工作、所有那些庞大的数据中心、所有那些重度计算和数以百万计的美元，都花在预训练阶段。但现在我们要进入一个稍便宜一些、却仍然极其重要的阶段，叫做后训练，在这里我们要把这个 LLM 模型变成一个助手。我们来看看，怎样才能让我们的模型不去采样互联网文档，而是去回答问题。换句话说，我们现在想做的是开始思考"对话"。这些对话可以是多轮的，也就是有多个回合。在最简单的情况下，它是一段人类和助手之间的对话。比如我们可以想象，对话可能是这样的：当人类说"2 加 2 等于几"时，助手应该回答类似"2 加 2 等于 4"。当人类接着追问"如果那个加号换成星号呢？"助手可以回答类似这样的内容。这里也是类似的，这是另一个例子，说明助手还可以带有某种性格，比如有点友善。然后在第三个例子里，我展示的是：当人类提出我们不想帮忙的事情时，我们可以产生一种所谓的拒绝（回答）（refusal），可以说我们无法帮忙处理这件事。换句话说，我们现在要做的是去思考一个助手应该如何与人类互动，我们要把助手及其在这些对话中的行为"编程"进去。

L77既然这是神经网络，我们就不会在代码里显式地编程——我们没法用那种方式去编程一个助手。因为这是神经网络，一切都是通过对数据集进行神经网络训练来完成的。正因如此，我们要通过创建对话数据集，来隐式地对助手进行编程。这就是一个数据集里三个独立的对话示例。一个真实的数据集——我等会儿会给你看例子——会大得多，可能包含数十万条多轮的、很长的对话，覆盖广泛多样的主题。但在这里我只展示了三个例子。顺便说一下，它的工作方式基本上是：助手是通过例子被"编程"的。那么这些数据是从哪来的呢？比如"2 乘 2 等于 4，和 2 加 2 一样"等等，这些是从哪来的？这来自人类标注员（human labeler）。我们基本上会给人类标注员一些对话上下文，然后请他们在这种情境下给出理想的助手回答。一个人类会针对任何情境，写出助手应当给出的理想回答；然后我们让模型基本上基于这些来训练，去模仿这类回答。于是它的工作方式就是：我们拿出在预训练阶段产出的基座模型。这个基座模型是在互联网文档上训练出来的。我们现在要拿走那个互联网文档数据集，把它丢掉，换上一个新的数据集——一个对话数据集。然后我们继续在这个对话数据集、这些对话上训练模型。结果是，模型会非常迅速地调整，去学习这个助手回应人类提问时的统计规律。之后在推理（inference）阶段，我们就能基本上引导这个助手、得到回答，而它会去模仿人类标注员在那种情境下会做的事——如果这么说你能明白的话。我们会看到一些这方面的例子，这也会变得更具体一些。我还想提一下，在这个后训练阶段我们基本上只是继续训练模型，但预训练阶段在实际中可能需要在数千台计算机上训练大约三个月。而后训练阶段通常要短得多，比如三个小时。这是因为我们在这里手工创建的对话数据集，比互联网上的文本数据集要小得多。所以这次训练会非常短，但从根本上说，我们只是拿过基座模型，继续训练——用完全相同的算法、完全相同的一切——只不过我们把数据集换成了对话。

L79那么现在的问题是：这些对话在哪里？我们怎么表示它们？我们怎么让模型看到的不再只是原始文本，而是对话？以及这种训练的结果是什么？当我们从某种心理学意义上谈论这个模型时，你得到的又是什么？我们现在就来看这些问题。我们先从对话的分词（tokenization）讲起。这些模型里的一切都必须被转换成词元（token），因为一切都只关乎词元序列。所以我们怎么把对话转换成词元序列呢？这就是问题所在。为此，我们需要设计某种编码方式。这有点像——如果你了解的话（不了解也没关系）——比如互联网上的 TCP/IP 数据包：对于如何表示信息、如何把所有东西组织到一起，都有着精确的规则和协议，以便所有这些数据都能以一种写在纸面上、大家都能达成一致的方式铺陈开来。所以在 LLM 里现在发生的是同样的事情：我们需要某种数据结构，也需要围绕这些数据结构（比如对话）如何与词元之间进行编码和解码，制定一些规则。现在我想给你看，我会如何在词元空间里重建这段对话。如果你打开 tiktokenizer，我可以把那段对话拿过来，这就是它在语言模型里被表示的样子。这里我们在一个两轮对话中交替出现一个 user 和一个 assistant。你在这里看到的，看起来很丑，但其实相对简单。它最终被转换成词元序列的方式有点复杂，但最终，这段 user 和 assistant 之间的对话变成了 49 个词元。它是一个由 49 个词元构成的一维序列，这些就是那些词元，好吗？而所有不同的 LLM 都会有一套略有不同的格式或协议，目前这有点像蛮荒的西部。不过举例来说，GPT-4o 是这样做的：你有一个叫做 im_start 的特殊词元，这是"imaginary monologue of the start（想象的内心独白之始）"的缩写。然后你必须指定——说实话我也不知道它为什么叫这个名字——你必须指定这一轮是谁的回合。比如 user，它对应词元 1、4、2、8。然后你有一个"内心独白分隔符"。接着就是问题本身，也就是问题的那些词元。然后你必须把它关闭，也就是 im_end，即"想象的内心独白"的结束。所以基本上，用户提出的"2 加 2 等于几"这个问题，最终就变成了由这些词元构成的词元序列。这里要强调的一点是，im_start 这并不是文本，对吧？im_start 是一个被加上去的特殊词元。它是一个新的词元。这个词元到目前为止从未被训练过——它是我们在后训练阶段创建并引入的一个新词元。于是这些特殊词元（比如 im_start 等等）被引入、穿插在文本之中，好让模型学到：嘿，这是一轮的开始——是谁的开始？是 user 的开始；然后这是 user 说的话，然后 user 结束。接着又是一轮新的开始，这次是 assistant 的；然后 assistant 说了什么？这些就是 assistant 所说话的词元，等等。于是这段对话就这样变成了这串词元序列。这里的具体细节其实并不重要。我想用具体方式向你说明的只是：我们把对话看作一种结构化的对象，而它最终通过某种编码，变成了一维的词元序列。既然它是一维的词元序列，我们就可以应用之前应用过的所有那些东西。现在它就是一个词元序列了，我们可以在它上面训练一个语言模型。我们依然是在预测序列中的下一个词元，就和之前一样，我们既能表示对话、也能在对话上训练。那么在测试时、在推理阶段，它又是什么样子呢？假设我们已经训练了一个模型，并且在这类对话数据集上训练过了。现在我们要做推理。那么当你在用 ChatGPT 时，推理是什么样子的？你来到 ChatGPT，跟它进行一段对话。它的工作方式大致是：假设这里已经被填好了——"2 加 2 等于几""2 加 2 等于 4"。现在你发出"如果换成乘号呢"，im_end。而在 OpenAI 之类的服务器上，基本上发生的事情是：他们放上 im_start、assistant、im_set，然后就停在这里。他们构造出这段上下文，然后开始从模型里采样。正是在这个阶段，他们会去问模型：好吧，好的第一个序列是什么？好的第一个词元是什么？好的第二个词元是什么？好的第三个词元是什么？而这就是 LLM 接管、生成回答的地方。比如，一个看起来大概像这样的回答——它不一定和这个完全一样，但如果这类对话出现在数据集里，它就会带有这种"风味"。所以协议大致就是这么工作的，虽然协议的细节并不重要。再说一遍，我的目标只是让你看到：一切都最终只是一个一维的词元序列，所以我们可以应用已经见过的所有东西，只不过我们现在不只是训练对话，也基本上是在生成对话。

L81好，现在我想转到这些数据集在实践中长什么样。我想给你看的第一篇论文、也是这个方向上的第一个成果，是 OpenAI 在 2022 年的这篇论文。这篇论文叫做 InstructGPT，或者说他们开发的这项技术。这是 OpenAI 第一次比较系统地讲述：如何把语言模型在对话上进行微调（fine-tune）。所以这篇论文里有不少细节，我想带你过一遍。我想停下的第一站是 3.4 节，那里讲到了他们雇的人类承包商——在这种情况下，是通过 Upwork 或者通过 Scale AI 招来的——来构造这些对话。所以这里有专业的人类标注员参与，他们的工作就是创作这些对话。这些标注员被要求想出各种提示词，然后再被要求给出理想的助手回答。所以这些就是人们想出来的那类问题。这些是人类标注员。比如"列出五个能让我重新对职业燃起热情的点子"、"接下来我该读的十大科幻小说有哪些？"这里有各种不同类型的提示词，比如"把这句话翻译成西班牙语"等等。所以这里有人们想出来的很多东西。他们先想出提示词，然后又自己回答这个提示词，给出理想的助手回答。那他们怎么知道，对于这些提示词，他们应当写出怎样的理想助手回答呢？当我们再往下滚动一点，会看到这里有一段摘录，是给人类标注员的标注指南（labeling instructions）。也就是说，开发这个语言模型的公司——比如 OpenAI——会写出标注指南，说明人类应该如何创作理想的回答。所以这里，举个例子，就是这类标注指南的一段摘录。在总体层面上，你要求人们做到乐于助人、真实可信、无害。如果你想看更多，可以暂停视频。但大体上就是：尽量回答，尽量乐于助人，尽量真实，不要回答那些我们不希望日后 ChatGPT 处理的问题。所以大致来说，由公司来制定标注指南。通常它们不会这么短，通常会有几百页，人们必须专业地研习它们，然后按照这些标注指南写出理想的助手回答。所以正如这篇论文所描述的，这是一个非常依赖人力的过程。

L83InstructGPT 的数据集其实从未被 OpenAI 公开过，但我们确实有一些开源的复现项目，试图遵循这种设置、收集自己的数据。比如我比较熟悉的一个，是之前 Open Assistant 的项目。这只是我认为众多例子中的一个，但我只想给你看一个例子。所以这里，这些是互联网上的人，被请来基本上创作这些对话，类似于 OpenAI 用人类标注员所做的那样。这里有一条某个人想出来的提示词："能不能请你写一段简短的介绍，讲讲经济学中买方垄断（monopsony）这个概念的相关性，请使用例子"等等。然后同一个人，或者可能是另一个人，会写出回答。所以这里是助手对这条的回答。于是同一个人或不同的人会实际写出这条理想回答。然后这是一个对话可以如何继续的例子——"现在把它解释给一只狗听"，于是你可以试着给出一个稍微简单一点的解释之类的东西。接着，这就成了标签，我们就以此进行训练。所以在训练中发生的事情是：我们当然不可能覆盖模型在推理测试时会遇到的所有可能问题。我们不可能涵盖人们将来会问的所有可能的提示词。但如果我们有一批这样的例子构成的数据集，那么模型在训练时就会逐渐开始扮演这个乐于助人、真实可信、无害的助手的角色。而这一切都是通过例子来编程的。这些都是行为的示例。如果你有这些示例行为的对话，而且数量足够多——比如 10 万条——并在此基础上训练，模型就开始理解这种统计模式，有点像渐渐拥有了这种助手的性格。当然，如果在测试时你得到的是完全一样的这个问题，回答有可能被一字不差地照着训练集复述出来，但更有可能的是，模型会做出某种"调性"相似的东西，而我们也会理解这就是你想要的那种回答。所以我们做的就是这样：我们通过例子来给系统编程，而系统在统计上采纳了这个乐于助人、真实可信、无害的助手的角色——这有点像公司所制定的那些标注指南的反映。

L85现在我想给你看的是，自 InstructGPT 论文以来，过去两三年里技术前沿已经有了进步。具体来说，现在人们已经不太常见完全靠人类独自承担所有重活了。这是因为我们如今有了语言模型，而这些语言模型在帮我们创建这些数据集和对话。所以人们会真的从零开始把回答写出来的情况已经很少见了；更可能的是，他们会用一个已有的 LLM 来基本上给出一个答案，然后对它进行编辑之类。所以现在有各种不同的方式，让 LLM 开始渗透进这个后训练的技术栈。LLM 基本上被用来、或者说被用来帮助创建这些海量的对话数据集。我想指出的是——其实我不想展示——UltraChat 就是这类更现代的对话数据集的一个例子，它在很大程度上是合成的，但我相信也有一些人类参与。这一点我可能记错。通常会有少量人类参与，但会有海量的合成辅助。而这一切都在以不同的方式被构造。UltraChat 只是当前存在的众多监督微调（SFT）数据集中的一个例子。我唯一想向你说明的是：这些数据集如今已经有数以百万计的对话。这些对话大多是合成的，但可能也在一定程度上被人类编辑过，并且横跨极其多样的领域等等。

L87所以到了现在，这些已经算是相当庞大的产物了，而且还有各种被称为 SFT 混合数据集的东西。里面混合了大量不同的类型和来源，一部分是合成的，一部分是人工的。从那以后，整体的方向大致也是这样。但大致来说，我们仍然有 SFT 数据集。它们由对话组成。我们就在这些数据上训练，就像之前那样。

L89我想说的最后一点是，我想稍微打破一点和 AI 对话的那种神秘感。当你在 ChatGPT 里输入一个问题，然后按下回车键，返回给你的东西，其实在统计意义上是和训练集里发生的事情对齐的。而这些训练集，说白了，最初的种子就是人类按照标注指南来操作的。那么你在 ChatGPT 里到底是在和什么对话，或者说你应该怎么理解这件事？嗯，大致来说，它并不是来自某种神奇的 AI。它来自某种在统计上模仿人类标注员的东西，而这些标注员遵循的是这些公司所写的标注指南。所以你其实就像是在模仿这个过程，你得到的，几乎就像是在向一个人类标注员提问。你可以想象，ChatGPT 给你的回答，某种程度上就是对一个人类标注员的模拟，就好像是在问：在这种对话里，一个人类标注员会怎么说。而且这个人类标注员并不是网上随便一个人，因为这些公司实际上会聘请专家。比如，当你问关于代码之类的问题时，参与构建这些对话数据集的人类标注员，通常都是受过良好教育的专家型人才。你就像是在向这些人的一个模拟体提问，如果你能理解的话。所以你不是在和某种神奇的 AI 对话，你是在和一个"平均的标注员"对话——这个平均的标注员可能技能相当高超，但你对话的，本质上是那种在构建这些数据集时会被雇来的人的一个瞬时模拟。

L91那么在我们继续之前，让我再给你举一个具体的例子。比如，当我在 ChatGPT 里说，推荐你见过的巴黎排名前五的地标。然后我按下回车。哦，好了，来了。当我按下回车，输出的是什么，我该怎么理解它？嗯，它不是某种神奇的 AI，跑出去研究了所有地标，然后用它无穷的智慧给它们排名等等。我得到的，是一个被 OpenAI 雇佣的标注员的统计模拟。你大致可以这样理解。如果这个具体的问题恰好就在 OpenAI 的后训练数据集里，那么我看到的回答，很可能就和那个标注员为这五个地标写下的内容非常非常相似。那个标注员是怎么得出这个结果的？嗯，他们会跑到网上，自己花大概二十分钟做点小研究，然后整理出一个清单，对吧？所以如果他们整理出了这个清单，并且它就在数据集里，我很可能就会看到他们提交的那个被当作正确答案的东西。

L93现在，如果这个具体的查询不在后训练数据集里，那我得到的回答就有点更"涌现"的味道了。因为模型在统计意义上大致理解，出现在巴黎的地标通常是那些显眼的地标，是人们通常想去看的地标，是在网上被非常频繁地谈论的那些地标。而且别忘了，模型在预训练阶段已经从互联网上学到了海量的知识。所以它可能见过大量关于巴黎、关于地标、关于人们喜欢看的东西的对话。所以正是预训练得到的知识，再加上后训练数据集，共同催生了这种模仿。这大致就是你可以用来理解幕后在统计意义上发生了什么的方式。

LLM 心理学：幻觉、工具与认知缺口

LLM 的许多奇怪行为不是偶然，而是由训练数据、token 表示、有限计算和上下文机制共同塑造。

回到顶部
核心观点

LLM 的许多奇怪行为不是偶然，而是由训练数据、token 表示、有限计算和上下文机制共同塑造。

观点

  • 幻觉来自模型学会了“自信回答”的格式，却未必知道自己不知道。
  • 参数中的知识像模糊回忆；上下文窗口里的内容像工作记忆，可靠性更高。
  • 模型每生成一个 token 的计算量有限，所以复杂推理需要展开成多个 token 或交给工具。
  • “瑞士奶酪”能力模型提醒我们：模型很多地方很强，但某些简单问题会突然失手。

定义

  • 工具调用模型输出特殊 token 或请求，让外部搜索、代码解释器等工具补充信息或执行计算。
  • 上下文窗口模型当前可直接访问的 token 范围，可视为工作记忆。
  • 系统消息隐藏在对话最前面的指令，用来设定身份、规则和行为边界。
  • 思维链把推理步骤展开成一串中间 token，让计算分布在多个生成步骤上。
  • 瑞士奶酪模型模型能力有洞：整体强大，但存在随机、局部、反直觉的失败点。

示例

  • 面对杜撰人物 Orson Kovats，旧模型可能编造履历，而不是说不知道。
  • 让模型总结《傲慢与偏见》第一章时，把原文贴进上下文通常比让它凭记忆更可靠。
  • 数 strawberry 里的字母、比较 9.11 和 9.9，都是视频中用来说明认知缺口的例子。

L127所以我想再次强调这个非常重要的、心理学层面的观点。神经网络参数里的知识，是一种模糊的回忆。构成上下文窗口的那些词元里的知识，是工作记忆。大致来说，它的运作方式和我们大脑里的运作方式很像。我们记住的东西就是我们的参数，而我们几秒或几分钟前刚刚经历过的事情等等，你可以想象它们就在我们的上下文窗口里，而这个上下文窗口是随着你周围有意识的体验而不断建立起来的。所以这对于你在实践中使用 LLM 也有很多启示。比如，我可以跑到 ChatGPT 里，做一件像这样的事情。

L129我可以说「请帮我概括一下简·奥斯汀《傲慢与偏见》的第一章」，对吧？这是一个完全没问题的提示词（prompt）。而 ChatGPT 在这里给出的回答其实相当合理。它之所以能做到这一点，是因为 ChatGPT 对《傲慢与偏见》这样著名的作品记得相当清楚。它很可能见过大量与之相关的内容，可能读过关于这本书的论坛讨论，也可能读过这本书的各种版本。它基本上是「记得」的，因为即便你只是读过这本书或相关文章，你也大致能记得足够多的内容，足以把这些都讲出来。但通常来说，我真正跟这些模型交互、希望它们回忆具体内容时，直接把内容喂给它们的效果总是更好。所以我认为一个更好的提示词应该是这样的：「请帮我概括简·奥斯汀《傲慢与偏见》的第一章，下面我把内容附上供你参考。」然后我加上一个分隔符，再把章节内容粘贴进去。这里我是从某个网站上复制粘贴下来的，把第一章复制进来。我这样做的原因是，当它处在上下文窗口（context window）里时，模型可以直接访问它，能够精确地使用它，而不必去「回忆」——它就是直接能拿到。所以这份概括的质量，预计会比之前那份概括明显更高，就因为内容对模型来说是直接可用的。我觉得你我做事也是同样的道理：如果你在概括之前重新读过这一章，你也会写出好得多的概括。这里发生的事情本质上就是这样，或者说是它的等价形式。

L131接下来我想简要谈一谈的另一个「心理小怪癖」，是关于「对自我的认知」。我在网上经常看到人们这样做：他们问大语言模型（LLM）一些问题，比如「你是什么模型，谁制造了你？」这个问题其实多少有点莫名其妙。我之所以这么说，是因为正如我之前试图用一些底层原理去解释的那样，这个东西并不是一个人，对吧？它没有任何意义上的持久存在。它基本上是启动、处理词元（token）、然后关闭。它对每一个人都是这样。它只是搭建起一段对话的上下文窗口，然后一切都被清除掉。所以这个实体在每一次对话中其实都是从零开始重新启动的，希望这能说通。它没有持久的自我，没有自我意识，它就是个「词元搅拌机」，按照训练集中的统计规律来填补词元。所以问它「你是谁、谁造的你」之类的问题，其实并不太说得通。而且默认情况下——如果你像我刚才描述的那样去做，仅仅是默认情况、什么都没做——你会得到一些相当随机的回答。比如，我们来拿 Falcon 开刀，这是一个相当老的模型，看看它会告诉我们什么。它在回避问题，「优秀的工程师和开发者」。这里它说：「我是由 OpenAI 基于 GPT-3 模型构建的。」这完全是它在瞎编。现在，这里说它是 OpenAI 构建的，我觉得很多人会据此认为这个模型是用 OpenAI 的数据训练出来的，或者诸如此类。我其实不认为这一定是真的。原因在于，如果你不显式地去编程让模型回答这类问题，那你得到的就是它在统计意义上对答案的最佳猜测。而这个模型有一个由对话构成的监督微调（SFT）数据混合，在微调过程中，随着在这些数据上训练，模型多少意识到自己正在扮演一个「乐于助人的助手」这样的人格。它并不知道、也确实没有人确切告诉过它该给自己贴上什么标签，它只是在扮演这个乐于助人的助手角色。还记得预训练阶段是把整个互联网的文档都拿来做训练的，而在这些文档里，ChatGPT 和 OpenAI 出现得非常频繁。所以我认为这里实际可能发生的事情是：这只不过是它对自己「是什么」所产生的幻觉性标签。它给自己定的身份就是「我是 OpenAI 的 ChatGPT」。它之所以这么说，只是因为互联网上有大量这样的回答，而这些回答实际上来自 OpenAI、来自 ChatGPT。所以那只是它对自己身份的标签。

L133作为开发者，你是可以覆盖这一点的。如果你有一个大语言模型，你实际上可以覆盖它。有几种方法可以做到。比如，我给你看 Allen AI 的这个 Olmo 模型。这是一个大语言模型，算不上顶级的那种，但我喜欢它，因为它是完全开源的。所以 Olmo 的论文以及所有其他东西都是完全开源的，这一点很棒。我们现在看的是它的 SFT 混合数据，也就是微调用的数据混合。这是对话数据集，对吧？他们为 Olmo 模型解决这个问题的办法是——我们看到这个混合数据里有一堆东西，总共有 100 万条对话，但这里我们看到 Olmo2 是硬编码进去的。点进去看，这是 240 条对话。看看这 240 条对话，它们都是硬编码的。「介绍一下你自己吧。」用户说。然后助手回答：「我是 Olmo，一个由 AI2——也就是 Allen Institute of Artificial Intelligence（艾伦人工智能研究院）——开发的语言模型」等等，「我在这里提供帮助」之类的。「你叫什么名字？」「Olmo 项目。」所以这些都是一些编出来的、硬编码的关于 Olmo2 的问题，以及在这些情况下应当给出的正确答案。如果你把像这样的 240 个问题或对话放进训练集并用它来微调，那么模型之后就会被期望去鹦鹉学舌地复述这些东西。如果你不这样做，那它大概会说自己是某个 AI 造的 ChatGPT。还有一种有时会用的方法是：基本上在这些对话里，你在人类和助手之间有多个轮次，有时候在对话最开头会有一条特殊消息，叫做「系统消息」。所以不只是人类和助手之间，还有一个系统。在系统消息里，你实际上可以硬编码并提醒模型：嘿，你是由 OpenAI 开发的模型，你的名字叫 ChatGPT-4o，你是用什么数据训练的、你的知识截止日期是什么，基本上就是把模型的「档案」写进去一点，然后这条系统消息会被插入到你的对话中。所以当你打开 ChatGPT 时你看到的是一个空白页面，但实际上系统消息是隐藏在里面的，那些词元就在上下文窗口里。所以这就是让模型谈论自己的两种编程方式：要么像这样通过数据来做，要么通过系统消息之类的、也就是那些存在于上下文窗口里、提醒模型自己身份的基本不可见的词元来做。但这一切都多少像是被编造出来、再外挂上去的东西，它并不是像对待人类那样真的、深刻地存在于模型内部。这一点要记住。

L135现在我想继续讲下一节，这一节涉及这些模型的计算能力，或者我应该说，涉及这些模型在解题场景中的「原生」计算能力。具体来说，在构造我们的对话示例时，我们必须对这些模型非常小心，这里有很多「棱角」，这些棱角在帮助我们理解这些模型如何「思考」时……很有启发意义，「elucidative」是这么拼吗？总之，当我们思考这些模型的思维方式时，这些棱角很值得一看。来看下面这段来自人类的提示词，假设我们基本上正在构建一段要放进训练集的对话。我们要拿这个来训练模型，教它怎么解决简单的数学题。提示词是这样的：「Emily 买了 3 个苹果和 2 个橙子，每个橙子 2 美元，总价是 13 美元，苹果的价格是多少？」非常简单的数学题。这里有两个答案，左边一个、右边一个。它们都是正确答案，都说答案是 3，这是对的。但其中一个对助手而言比另一个要好得多。如果我是个标注员、要创建其中之一的话，其中一个是助手的极差答案，另一个则还可以。所以我想让你——可能的话暂停视频——想想这两个答案里为什么有一个比另一个好得多。如果你用了错的那个，你的模型在数学上可能会变得很差，效果会很糟。这一点你在编写标注指南、培训人们去为助手创建理想回答时，是必须非常小心的。

L137好，这个问题的核心在于要意识到并记住：当模型在训练以及推理（inference）时，它们都是在一个从左到右的一维词元序列上工作的。这就是我脑海中常常浮现的画面：我想象词元序列从左向右逐步展开，而为了总是产生序列中的下一个词元，我们把所有这些词元喂进神经网络。这个神经网络会为序列中的下一个词元给出概率，对吧？这张图就是我们之前在上面看到过的那张，它来自我之前给你演示过的网页 demo，对吧？这个计算基本上就是接收顶部的输入词元，在所有这些神经元上执行运算，然后给出接下来会出现什么的概率答案。

L139现在要意识到的重要一点是，大致上，这里发生的计算层数是有限的。比如，这里的这个模型只有 1、2、3 层所谓注意力和 MLP。一个典型的现代最先进网络层数会更多，比如大概 100 层之类的。但从「之前的词元序列」到「下一个词元的概率」，也只有大约 100 层计算之类的。所以这里对每一个单独的词元，都只发生有限数量的计算。你应该把这看作是一个非常小的计算量。而这个计算量在这个序列中，对每一个词元而言几乎大致是固定的。这并不完全准确，因为你喂入的词元越多，这个神经网络的前向传播（forward pass）就越昂贵，但贵不了多少。所以你应该把它——我觉得这是个值得放在脑海中的好模型——看作是：这个盒子里对每一个词元都会发生一个固定大小的计算。而这个计算量不可能太大，因为从顶部到底部的层数也就那么多，这里能发生的计算量也就那么多。所以你不能指望模型在单次前向传播里、为了一个词元就去做任意复杂的计算。这就意味着，我们实际上必须把推理和计算分散到许多词元上去完成，因为每一个单独的词元只能获得有限的计算量。所以我们希望把计算分散到很多词元上，而不能在任何一个单独的词元上期待或要求模型做太多计算，因为每个词元里能发生的计算也就那么多，明白吗？大致就是这样一个固定的计算量。

L141所以这就是为什么这边这个答案要差得多。原因在于：想象从左到右，我把答案粘在这里了——「答案是 3」等等——想象模型必须从左到右、一次一个词元地把它们吐出来。它得说、或者我们期望它说「答案」「是」「空格」「美元符号」，然后就在这里，我们期望它把这道题所有的计算都塞进这一个单独的词元里。它必须吐出正确的答案「3」。而一旦我们吐出了答案「3」，我们还指望它说后面这一堆词元，但到了这一步，我们已经把答案生产出来了，它已经躺在上下文窗口里了，后面这些词元都只是事后为「为什么这是答案」找的辩解，因为答案已经被创造出来了，已经在词元窗口里了。所以它其实并没有在这里被计算。因此，如果你直接、立即作答，你就是在训练模型去试图在一个词元里把答案猜出来。而这根本行不通，因为每个词元的计算量是有限的。这就是为什么右边这个答案好得多：因为我们把计算分散到了整个答案中。我们实际上是在让模型慢慢地、从左到右地走向答案。我们得到了中间结果，我们在说：「好，橙子的总成本是 4。所以 13 减 4 等于 9。」我们就这样造出一个个中间计算，而每一个这样的计算本身都不那么费事。我们其实多少是在试探模型在任何一个单独词元里能胜任的难度。这里任何一个词元里的计算都不能太重，否则模型在测试时就做不出来了。所以我们在这里教模型把它的推理展开、把计算分散到各个词元上。这样一来，每个词元里只有非常简单的问题，而它们可以累加起来。等到接近末尾时，它的工作记忆里已经有了之前所有的结果，要确定答案就容易多了——就是这里，3。所以这是一个明显更好的标注。另一种就是很糟糕，它在教模型把所有计算都挤进一个词元里，非常糟糕。

L143所以这是值得记住的一个有趣之处：在你写提示词时通常不必显式地操心这件事，因为 OpenAI 那边有标注员之类的人专门操心这个，确保答案是展开的。所以 OpenAI 基本上会做对。当我把这道题问 ChatGPT 时，它其实会走得很慢，会像「好，我们来定义变量，列出方程」这样，它正在造出所有这些中间结果。这些不是为了给你看的，是给模型自己用的。如果模型不为自己创造这些中间结果，它就没法走到「3」这个答案。

L145我还想给你看，对模型「使点坏」也是可能的。我们可以直接命令它。举个例子，我给了它完全一样的提示词，然后说：「用一个词元作答，直接给我答案，什么别的都别说。」结果对于这道简单的提示词，它竟然一次就做出来了。它只产生了一个——我想这是两个词元吧，因为美元符号本身是一个词元。也就是说，这个模型没给我一个词元，而是给了两个，但它仍然给出了正确答案。它是在单次前向传播网络里完成的。那是因为这里的数字我觉得非常简单，所以我把它弄得更难了一点，对模型狠一点。我设 Emily 买 23 个苹果和 177 个橙子，把数字弄大一点，就是让它更难。我是在要求模型在单个词元里做更多计算，所以我还是设成那样，而它给了 5，5 实际上是不对的。所以模型没能在单次前向传播网络里完成所有这些计算。它没能从输入词元出发，在单次穿过网络的过程中直接给出结果。然后我说：「好，现在别管词元限制了，就按通常方式解题。」于是它就一路列出所有中间结果，一路化简，每一个中间结果、每一次中间计算对模型来说都更容易。每个词元里也没有太多工作量，这里所有词元都是对的，最后它得到了答案，7。它就是没法把所有这些工作量挤进单次前向传播网络里。所以我觉得这是个挺有意思的例子，值得想一想，我认为它同样很有启发性，能说明这些模型是怎么工作的。

L147关于这个话题我想说的最后一点是：如果我在日常中真的要解这道题，我可能不会完全相信模型把所有这些中间计算都做对了。所以实际上我大概会这样做：我会过来说「使用代码」。那是因为代码是 ChatGPT 可以使用的工具之一。与其让它做这种心算——就像这里的心算，我不太信得过，尤其是数字很大时，没法保证模型能做对。这里任何一步中间计算都可能失败。我们是在用神经网络做心算，就像你在脑子里做心算一样，它可能就在某个中间结果上搞砸了。它能做这种心算其实挺惊人的，我自己大概没法在脑子里算出来，但模型基本上就是在「脑子里」算的，而我不信这个。所以我想用工具。你可以说类似「使用代码」这样的话。我有点不确定那边发生了什么，「使用代码」。就像我提到的，这里有一个专门的工具，模型可以写代码，而我可以检查这段代码是否正确。然后它就不再依赖自己的心算，而是用 Python 解释器——一种非常简单的编程语言——把算结果的代码写出来。我个人会远比相信它心算更相信这个，因为这是从 Python 程序里跑出来的，我觉得 Python 在正确性保证上比语言模型的心算要强得多。所以这又是一个小提示：如果你遇到这类问题，可能最好就是让模型使用代码解释器。而且就像我们在网页搜索那里看到的一样，模型有专门的调用词元。它实际上不会从语言模型里生成这些词元，而是会写出程序，然后把那个程序发送到计算机里另一部分去真正运行、把结果带回来。之后模型就能拿到那个结果，可以告诉你「好，每个苹果的成本是 7」。所以这是又一种工具，实际中你会自己用它，而且我认为它更不容易出错。

L149所以这就是我把这一节叫做「模型需要词元来思考」的原因。把计算分散到许多词元上，让模型创造中间结果，或者尽可能借助工具和工具调用，而不是任由模型把这一切都在它的工作记忆里搞定。如果它试图全在记忆里搞定，我不太信得过，所以我尽可能用工具。

L151我还想再给你看一个这种现象出现的地方，那就是「计数」。模型其实不擅长计数，原因完全一样：你要求在单个词元里做的事情太多了。我给你看一个简单的例子。「下面有多少个点」，然后我就放进去一堆点。ChatGPT 说「有」，然后就试图在一个词元里把这道题解出来。在单个词元里，它必须数出上下文窗口里点的个数，而且必须在单次前向传播网络里做到。单次前向传播网络里，正如我们谈过的，能发生的计算没那么多，你就把它想成那里只发生很少的计算。所以如果我看看模型实际看到的是什么，我们去 LLM 那里、去分词器（tokenizer）看：它看到的是「下面有多少个点」，然后结果这些点，这一组我想大概 20 个点，是一个单独的词元。然后这一组、不管多少个，是另一个词元。然后出于某种原因，它们这样断开。我其实不——这跟分词器的细节有关，但结果是这些模型基本上看到的是词元 ID，这个、这个、这个，等等。然后要从这些词元 ID 去数出数量来。剧透一下，不是 161，实际是——我记得是 177。所以我们能这样做：我们说「使用代码」。你可能会觉得，为什么这样会管用？这其实挺微妙也挺有意思。当我说「使用代码」时，我其实预期它管用，我们来试试。好，177 是对的。这里发生的事情是，我实际上——虽然看不出来——把这道题拆成了对模型来说更容易的子问题。我知道模型不会数数，它没法心算着数。但我知道模型其实相当擅长复制粘贴。所以我做的是：当我说「使用代码」时，它在 Python 里为此创建了一个字符串，而把我的输入从这边复制粘贴到那边的任务非常简单。因为对模型来说，它看到这串字符——它只是把这些看作那四个词元或类似的东西。所以对模型来说，复制粘贴那些词元 ID、把它们解包成这里的点，是非常简单的。于是它创建了字符串，然后调用 Python 的相应函数去计数，最后得到了正确答案。所以做计数的是 Python 解释器，而不是模型的心算。这又是一个简单的例子：模型需要词元来思考，别依赖它们的心算，这也正是为什么模型不擅长计数的原因。如果你需要它们做计数任务，永远要求它们借助工具。

L153模型还有许多其他这里那里的小「认知缺陷」，这些都是这项技术随着时间推移需要去留意的「棱角」。举个例子，模型在各种与拼写相关的任务上不太行，它们不擅长这个。我说过我们会回头再讲分词（tokenization），原因就是：模型看不到字符，它们看到的是词元。它们的整个世界都是词元，也就是这些小文本块。它们不像我们的眼睛那样看到字符。所以非常简单的字符级任务经常会失败。比如，我给它一个字符串 ubiquitous，让它只打印从第一个开始每隔第三个字符。我们从 u 开始，然后每隔三个——一、二、三，下一个应该是 q，以此类推。这里的「ic」是不对的。我的假设同样是：这里又是心算出了问题——第一，多少有点；第二，我认为更重要的问题是，如果你去分词器看，看 ubiquitous，我们会看到它是三个词元，对吧？你和我看到 ubiquitous，我们能轻易访问其中的单个字母，因为我们看得到它们；当它们在我们视觉的「工作记忆」里时，我们可以很容易地索引到每隔第三个字母，我能完成这个任务。但模型没法访问单个字母，它把这个词看成这三个词元。而且别忘了，这些模型是从零开始、在互联网上训练出来的，模型必须自己去发现：所有这些不同的字母，到底是怎么被打包进所有这些不同的词元里的。

L154我们之所以要使用词元（token），主要还是为了效率。不过我觉得很多人其实很想彻底抛弃 token，比如改用字符级或字节级的模型。问题只在于那样会产生非常长的序列，而大家目前还不知道该如何处理这种情况。所以在 token 的世界里，任何与拼写相关的任务其实都不太可能表现得太好。正因为我清楚由于分词的存在，拼写并不是模型的强项，所以我可以再次让它借助工具。我只需说"使用代码"。我同样预期这次会成功，因为把 ubiquitous 复制粘贴到 Python 解释器里这个任务要简单得多，然后我们就依赖 Python 解释器去操作这个字符串中的字符。所以当我说"使用代码"时，让 ubiquitous 每隔第三个字符取一个索引，得到的结果是 uq2s、uqts，我觉得看起来是对的。所以这又是一个拼写相关任务表现不佳的例子。

L156最近一个非常著名的例子就是"strawberry 里有几个 a"，这个例子在网上疯传了很多次。现在模型基本上都能答对了，它们会说 strawberry 里有三个 r。但在很长一段时间里，所有最先进的模型都坚持说 strawberry 里只有两个 r。这引起了不小的轩然大波——这个词算是个时髦词吧，我觉得算，因为大家就是纳闷：这些模型怎么会这么聪明？它们能解奥数题，却数不清 strawberry 里有几个 r。答案呢，我可以慢慢铺垫着讲。第一，模型看到的根本不是字符，而是 token。第二，模型本来就不太擅长计数。所以这里我们既叠加了"看不到字符"的困难，又叠加了"计数"的困难，这正是模型在这个问题上栽跟头的原因。不过说实话，我觉得到如今 OpenAI 可能已经把这个答案硬编码进去了，我也不确定他们具体做了什么，但这条特定的查询现在确实能答对了。

L180所以如果我们唯一在乎的就是到达最终答案，并且把"呈现给人类"这件事单拎出去，那我们其实并不真的知道该怎么标注这个例子。我们不知道该给 LLM 哪一条解法，因为我们不是 LLM。在数学这种例子上这点很清楚，但这其实是个相当普遍的问题——比如，我们的知识并不等于 LLM 的知识。LLM 在数学、物理、化学这些博士级别的内容上其实拥有大量知识，很多方面它懂得比我多。而我可能并没有在它解题时把这些知识利用起来。但反过来，我可能又在解法里塞进了一堆 LLM 参数里并不具备的知识，于是对模型来说就出现了这种突兀的跨越，非常让人困惑。所以我们的认知方式是不同的，如果我们只在乎到达最终解、并且最好还能经济地到达，那我真的不知道这里该放什么。长话短说：我们并不处在为 LLM 编造这些 token 序列的好位置上。靠模仿它们能用来初始化这个系统，但我们真正想要的是，让 LLM 自己去发现对它管用的那些 token 序列。它需要自己去找到，在给定提示词的情况下，哪一种 token 序列能可靠地通向答案。而这件事，我们要通过强化学习、通过不断试错来发现。

L182那我们来看看这道例子在强化学习里会怎么运作。好，我们现在回到了 Hugging Face 的推理（inference）游乐场。它能让我很方便地调用各种不同的模型。比如右上角我选了 Gemma 20 亿参数的模型。20 亿非常非常小，所以这是个很小的模型，但没关系。我们要给它……强化学习基本上怎么运作其实很简单：我们需要尝试很多种不同的解法，看看哪些管用、哪些不管用。我们基本上就是拿到提示词，跑这个模型，模型生成一个解法，然后我们去检查这个解法。我们知道这道题的正确答案是 3 美元，果然模型答对了，是 3 美元。所以这是对的，这只是对解法的一次尝试。现在我们把它删掉，再跑一次。来试第二次。这次模型用了略微不同的方式解题，对吧？每一次尝试都是一次不同的生成，因为这些模型是随机系统。记得吗，在每一个 token 上我们都有一个概率分布，我们是从那个分布里采样，所以我们会走到略微不同的路径上去。于是这又是一个最终得到正确答案的解法。现在我们把它删掉。第三次走起。好，又是一个略有不同的解法，但也答对了。我们可以把这个过程重复很多次。实际上你可能会对单个提示词采样上千条独立解法，甚至上百万条。其中一些会是对的，一些就不太对。而我们想做的，基本上就是鼓励那些能导向正确答案的解法。

L184我们来看看那会长什么样。如果回到这里，这儿有一张示意图，展示的就是这个情况：我们有一个提示词，然后我们并行尝试了许多不同的解法。有些解法走得很顺，得到了正确答案，用绿色表示；有些解法走得很糟，没能得到正确答案，用红色表示。不过很遗憾，这道题不是最好的例子，因为它太简单了——我们看到即便是 20 亿参数的小模型也总是能答对。从这个意义上说它不是最好的示例。但让我们发挥一下想象力，就假设绿色是好的、红色是坏的，好吗？我们生成了 15 条解法，其中只有 4 条得到了正确答案。那现在我们要做的，就是鼓励那些能导向正确答案的那一类解法。那些红色解法里不管出现了什么 token 序列，显然某处出了岔子，这不是一条走通的解题路径；而绿色解法里那些 token 序列，情况就很好。于是我们就希望在未来面对这类提示词时，多走这种路。而我们用来在未来鼓励这种行为的办法，就是去在这些序列上做训练。但这些训练序列现在不是来自专家级的人类标注员——并没有哪个人类来认定这条解法是正确的，这条解法是模型自己生成的。所以模型在这里就是在练习：它试了几条解法，其中四条看起来管用，于是模型就有点像是在这上面训练。这就好比一个学生审视自己的解法，心想：好吧，这条很奏效，那我以后就该这么解这类题。

L186在这个例子里，其实有很多种方式可以去微调这套方法论，但要把核心思想讲清楚，最简单的也许是直接从这四条里挑出最好的那一条——比如这一条，所以它被标成了黄色。这条不仅得到了正确答案，可能还具有其他一些好性质：也许它最短，也许某种意义上最好看，又或者你能想到别的什么标准。我们把它定为这条最优解，去训练它。这样做了参数更新之后，未来再遇到这种情形，模型就会更可能走这条路。但你得记住，我们会在成千上万种各不相同的提示词上跑这个——横跨大量数学题、物理题等等等等。所以心里要有个数：可能有几万条提示词，每条又有上千条解法，而这一切基本上是在同时进行的。随着我们不断迭代这个过程，模型就在自己发现什么样的 token 序列能让它得到正确答案。这并不来自人类标注员，模型有点像是在这个游乐场里玩耍，它知道自己想达到什么，然后在发现那些对它管用的序列——这些序列不做任何思维上的大跳跃，统计上也可靠地管用，并且充分利用了模型自身已有的知识。这就是强化学习的过程：本质上就是猜测和检验，我们会去猜很多种解法，去检验它们，然后在未来多做那些管用的事。这就是强化学习。

L188那么对照之前讲过的，我们现在看到 SFT 模型，也就是监督微调模型，依然是有用的，因为它依然在某种程度上把模型初始化到了正确解法的附近。它有点像是对模型的一种初始化。

L189也就是说，它大致能让模型把解答写出来，也许它理解了如何建立方程组，或者它会把一道题的解法大致讲一遍。所以它能把模型带到接近正确答案的范围内。但真正把一切打磨到位的是强化学习（RL）。我们真正发现对模型有效的解法，得到正确答案，然后鼓励这些解法，模型就会随着时间不断变好。

L191好的，这就是训练大语言模型（LLM）的高层流程。简单来说，我们训练它们的方式和训练小孩非常相似。基本上唯一的区别在于，小孩是按一本书一本书的章节推进的，他们在每一章里完成各种不同类型的练习。而训练 AI 时，几乎像是按照每个阶段的类型，一个阶段一个阶段地推进。

L193首先我们做的是预训练，正如我们所见，它相当于基本上读完所有的讲解性材料。我们同时打开所有的教材，通读所有的讲解，努力建立一个知识库。

L195接下来我们进入监督微调（SFT）阶段，这一阶段实际上是在看所有教科书中、各领域人类专家给出的那些标准解答。于是我们得到一个 SFT 模型，它能模仿专家，但只是盲目地模仿。它只是在尽力做出最好的猜测，在统计上尽量去模仿专家的行为。这就是你看完所有标准解法后得到的东西。

L197最后，在最后一个阶段，也就是强化学习阶段，我们把所有教科书里的练习题都做一遍。于是我们就得到了强化学习模型。所以从高层来看，我们训练 LLM 的方式，非常等同于训练小孩的那套流程。

L199我想说的下一点是，其实前两个阶段——预训练和监督微调——已经存在多年了，它们非常标准化，每一家 LLM 提供商都在做。真正还处在发展早期、尚未在业内标准化的，是最后这个强化学习训练阶段。这个阶段还相当初期和新兴。

L201原因在于，我刚才在这个过程中其实略过了大量细节。核心想法非常简单，就是试错学习，但具体到如何挑选出那些最优解法、在它们上面训练多少、提示词（prompt）的分布是什么、以及如何设置训练流程才能让这一切真正奏效，其中有大量细节和数学上的微妙之处。所以核心思路极其简单，但它背后有许许多多的细节和旋钮。要把这些细节做对并不容易。

L203因此，很多公司——比如 OpenAI 和其他 LLM 提供商——内部已经对 LLM 的强化学习微调试验了一段时间，但他们并没有公开谈论这件事，基本都在公司内部进行。这也是为什么 DeepSeek 最近发表的那篇论文会如此轰动，因为这是来自中国一家名叫 DeepSeek AI 的公司。这篇论文非常公开地讨论了大语言模型的强化学习微调，讨论了它对大语言模型有多么重要，以及它如何能在模型中激发出大量推理能力——这一点我们一会儿就会讲到。所以这篇论文重新点燃了公众对把强化学习用于 LLM 的兴趣，并且给出了相当程度的细节，足以复现这些结果，真正让这个阶段在大语言模型上跑起来。

核心观点

RLHF 用奖励模型模拟人类偏好，让主观任务也能训练；但奖励模型不是现实本身，容易被对抗样本利用。

观点

  • 写诗、讲笑话、摘要这类任务没有唯一正确答案，不能像数学题那样直接验算。
  • 人类更容易判断两个回答哪个好，而不一定容易亲手写出最优回答。
  • 奖励模型能扩展人类反馈，但它会被 RL 找到漏洞，所以 RLHF 通常不能无限跑。

定义

  • 不可验证领域没有明确标准答案、需要人类主观判断质量的任务。
  • RLHFReinforcement Learning from Human Feedback，基于人类反馈的强化学习。
  • 奖励模型学习模仿人类偏好排序的独立模型，用来给候选回答打分。
  • 判别器-生成器差距判断好坏通常比亲自生成高质量作品更容易。
  • 对抗样本专门钻模型漏洞、让模型给出异常高分的输入或输出。

示例

  • 人类给多首诗或多个笑话排序，奖励模型学习这种排序偏好。
  • 奖励模型可能把无意义重复文本打高分，于是 RL 会把笑话训练到崩坏。

L271所以我们要改用 RLHF 的办法。在 RLHF 里，核心技巧其实就是「间接」（indirection）这一招。我们只让人类参与一点点，而我们「作弊」的方式是：我们单独去训练一个完整的神经网络，称之为奖励模型（reward model）。这个神经网络会去模仿人类的打分。我们先让人类给各种生成结果打分，然后用一个神经网络去模仿这些人类打分。于是这个神经网络就变成了某种「人类偏好的模拟器」。现在有了这么一个神经网络模拟器，我们就可以拿它当对象来做 RL 了。也就是说，我们不再是去问一个真实的人类，而是去问一个「模拟的人类」，问它觉得某个笑话能打多少分。一旦有了模拟器，我们就一路畅通了，因为我们可以任意次地查询它，整个过程完全自动化，我们就能针对这个模拟器来做强化学习。而这个模拟器，正如我们所料，不会是一个完美的人类，但只要它在统计意义上与人类的判断足够相似，你就可以预期这样做是有效果的。而在实践中也确实如此。所以一旦有了模拟器，我们就能跑 RL，一切都很顺利。

L275奖励模型是一个完全独立的神经网络，一个单独的网络。它大概也是个 Transformer，但它不是那种会生成各种语言的「语言模型」，它只是一个打分模型。奖励模型的输入是两样东西：一是提示词，二是一个候选笑话。这就是进入奖励模型的两个输入。比如这里，奖励模型接收的就是这条提示词和这个笑话。奖励模型的输出是一个单一的数字，这个数字被当作分数，它的范围比如可以从 0 到 1。0 是最低分，1 是最高分。这里有一些例子，展示训练过程中某个阶段的奖励模型会怎么给这些笑话打分：0.1 是很低的分，0.8 是相当高的分，依此类推。然后我们拿奖励模型给的分数，去和人类给出的排序做对比。这里有一种精确的数学方法来计算它，基本上就是设定一个损失函数，算出对应关系，然后据此更新模型。但我只想给你一个直觉：比如对于第二个笑话，人类觉得它最好笑，模型也基本同意，0.8 是个相对较高的分。但这个分其实应该更高才对。所以更新之后，我们预期这个分在网络更新后会再涨一点，比如变成 0.81 左右。而对于这条，模型和人类存在严重分歧，因为人类把它排第 2，但这里它只得 0.1 分，所以这个分应该高得多。于是在这类监督之上做一次更新后，这个分可能会涨很多，也许变成 0.15 之类的。再看这里，人类觉得这是最差的笑话，但模型却给了它一个相当高的分，所以你可以预期更新之后它会掉下来，也许掉到 3.5 左右。基本上我们做的还是和之前一样的事：用神经网络的训练过程，轻轻地微调模型的预测，努力让奖励模型的分数与人类的排序保持一致。随着我们在人类数据上不断更新奖励模型，它就越来越能模拟人类给出的分数和排序，最终成为人类偏好的模拟器，我们再拿它来做 RL。但关键是，我们并不是让人类去看 10 亿次笑话。我们大概只看上千条提示词、每条若干个笑话，所以人类总共要看的大概是 5000 个笑话。他们只给个排序，然后我们就训练模型去和那个排序保持一致。数学细节我就略过了。我只想让你理解一个高层思路：这个奖励模型基本上就是给我们打分，而我们有一种方法，能把它训练得与人类的排序相一致。RLHF 就是这么运作的。

L277好，这就是大致的想法。我们基本上训练了人类的模拟器，然后对这些模拟器做 RL。现在我想先讲讲 RLHF 的好处。第一，它让我们能够跑强化学习——我们知道强化学习是一套极其强大的技术——而且让我们能在任意领域里跑，包括那些不可验证的领域。比如摘要、诗歌写作、笑话写作，或者任何其他真正的创意写作，在数学和代码之外的领域等等。从经验上看，当我们真正应用 RLHF 时，它会提升模型的性能。我有一个关于「为什么会这样」的最佳猜测，但我其实并不确定这个原因是否像前面那些结论一样有充分的依据。你可以经验性地观察到：当你正确地做了 RLHF，得到的模型就是会好一点点。至于为什么好，我觉得并不是那么清楚。这是我的最佳猜测。我的猜测是，这可能主要归因于「判别器—生成器差距」（discriminator generator gap）。它的意思是，在很多情况下，对人类来说，判别比生成要容易得多。具体来说，当我们做监督微调（SFT）时，我们要求人类生成理想的助手回答。在很多情形下，就像我展示的那样，理想的回答很容易写。但在很多情形下并非如此。比如摘要、写诗、写笑话，你作为人类标注员，要怎么在这些情况下写出理想的回答？这需要人类去进行创作。而 RLHF 恰恰绕过了这一点，因为我们可以给数据标注员一个容易得多的问题：他们不需要直接去写诗，而是模型给他们五首诗，让他们排个序就行。这对人类标注员来说是一项容易得多的任务。所以我觉得这基本上能让我们获得更高准确率的数据，因为我们没有要求人们去做那种极其困难的生成任务。我们没让他们去搞创意写作，只是让他们分辨不同的创意作品、挑出最好的。人类提供的信号就是这个排序，这就是他们给系统的输入。然后系统在 RLHF 里会自己去发现那些会被人类打高分的回答。正是这一层间接，让模型变得越来越好。这就是 RLHF 的好处：它让我们能跑 RL，从经验上看能产出更好的模型，也让人们能在不必承担极端困难任务（比如写理想回答）的情况下贡献监督信号。

L279不过很遗憾，RLHF 也伴随着重大的缺点。主要的一个是：我们做强化学习，并不是针对真实的人类和真实的人类判断，而是针对人类的一种「有损模拟」。这个有损模拟可能会产生误导，因为它毕竟只是个模拟，只是一个输出分数的语言模型，未必能在所有可能的情况下都完美反映一个真正长着脑子的人类的真实看法。这是第一个问题。其实还有一种更微妙、也更刁钻的情况，它严重地拖了 RLHF 作为一项可扩展到真正智能系统的技术的后腿。那就是：强化学习极其擅长发现怎么去「钻」这个模型、去钻这个模拟器的空子。我们这里构建的这个会打分的奖励模型，这些模型都是 Transformer。这些 Transformer 是庞大的神经网络，有几十亿个参数，它们在模仿人类，但只是以一种「模拟」的方式模仿。问题在于，这些是庞大、复杂的系统，这里有几十亿个参数在输出一个单一分数。事实证明，这些模型是可以被钻空子的。你能找到一些输入，它们不属于模型的训练集，却莫名其妙地拿到极高的分数，但这种分数是假的。所以你经常会发现，如果你把 RLHF 跑很久——比如我们做 1000 次更新，算很多次了——你会预期你的笑话越来越棒、能拿到关于鹈鹕的绝世金句，但其实并不是那样。实际发生的是：在头几百步里，关于鹈鹕的笑话大概会改善一些，然后它们会突然断崖式下滑，你开始得到完全无意义的结果。比如，你开始得到「最佳鹈鹕笑话」是「the the the the the」之类的，这毫无道理，对吧？你看着它，心想凭什么这是最佳笑话？但当你把它塞进你的奖励模型里，你预期它会得 0 分，可奖励模型却爱死它了，它会告诉你「the the the the the」得 1.0 分，是最佳笑话，这完全说不通。这是因为这些模型只是人类的模拟器，它们是庞大的神经网络，你能在输入空间的最底端找到一些输入，钻进模型的某个角落，得到无意义的结果。这些例子就是所谓的「对抗样本」（adversarial examples），这个话题我不展开讲，但它们就是模型的对抗性输入。它们是一些特定的小输入，钻进模型的缝隙和角落里，在顶端吐出无意义的结果。

L281现在，你可以想象这样做：你说，好吧，这显然不该是 1 分，这显然是个低分，那我们把它加进数据集，给它一个极差的排序，比如第 5 名。确实，你的模型会学到「the the the the the」应该得极低的分，于是给它 0 分。但问题在于，模型里总是藏着无穷多个无意义的对抗样本。如果你把这个过程迭代很多次，不断把无意义的东西加进奖励模型、给它们极低的分，你永远赢不了这场游戏。你可以这么做很多很多轮，而强化学习只要跑得够久，总能找到钻模型空子的办法。它会发现对抗样本，用无意义的结果拿到超高分。从根本上说，这是因为我们的打分函数是一个巨型神经网络，而 RL 极其擅长找到欺骗它的办法。所以长话短说：你总是让 RLHF 跑个几百次更新，模型在变好，然后你就得截断、收工。你不能对着这个奖励模型跑太久，因为优化过程会开始钻它的空子。你基本上就是截断、叫停、发布。你可以改进奖励模型，但最终你总会在某个时刻撞上这种局面。所以我常说：RLHF 不是 RL。我的意思是，RLHF 显然是 RL，但它不是那种「神奇意义上的 RL」。这不是你能无限期跑下去的 RL。像那种有确定正确答案的问题，你就没法这么容易地钻空子——你要么答对了、要么没答对，打分函数也简单得多，你只要看框出来的那块、看结果对不对就行。所以这种函数很难被钻空子，但钻奖励模型的空子却是可能的。而在这种「可钻空子」的领域里……嗯，在像围棋那样有完美模拟器的领域里，你反而可以无限期地跑 RL，你可以跑几万步、几十万步，发现各种我们人类根本想不到的、性能极佳的疯狂策略。在围棋里，你没法在「赢棋/输棋」这件事上钻空子。有了完美的模拟器，我们知道每一颗棋子摆在哪，能算出某个人到底有没有赢，这个没法钻空子。所以你可以无限期地跑 RL，最终连……至少都能超过某个水平。但对于这种可钻空子的模型，你没法无限重复这个过程。所以我某种程度上把 RLHF 看作「不是真正的 RL」，因为它的奖励函数是可钻空子的。它更像是某种「轻微的微调」。它是一点点改进，但它并不是从根本上是「正确搭好了」的那种——那种你能往里灌更多算力、跑更久、得到更好更神奇结果的搭法。从这个意义上说它不是 RL。说它不是 RL，是说它缺乏那种魔力。它可以微调你的模型、提升性能。事实上，如果我们回到 ChatGPT，GPT-4o 模型就经过了 RLHF，因为它确实管用。但它只是「不是那种意义上的 RL」。RLHF 就像一次小小的微调，让你的模型稍微变好一点。我大概会这么去理解它。

L309现在让我们绕回到我们出发的地方。问题是：当我们打开 chatgpt.com，输入某个查询，然后点下回车，这里到底发生了什么？我们看到的是什么？我们在和谁对话？这一切是怎么运作的？我希望这个视频让你对一些「引擎盖下」的细节有所体会——这些模型是如何训练的，返回给你的又究竟是什么。

L311具体来说，我们现在知道了：你的查询被拿到之后，首先会被切成词元。所以我们来到分词器（tokenizer）。这里有一个用于用户查询的格式位置，我们基本上就把自己的查询填在那里。于是我们的查询进入了我们之前讨论过的对话协议格式，也就是我们用来维护对话对象的这种方式。它被插到那里去。然后这一整套东西，在底层就变成了一串词元序列，一维的词元序列。所以 ChatGPT 看到的是这串词元序列。然后当我们点下「go」时，它基本上就是不断往这个列表里追加词元，延续这个序列，它就像一个词元自动补全器。具体而言，它给出了这段回复。我们可以把它放在这里，就能看到它续写出来的词元，这些就是它大致续写出来的词元。

L313那么问题就来了：为什么模型回应的就是这些词元？这些词元是什么？它们从哪儿来？我们在和什么对话？我们又该如何给这个系统编程？于是我们转换了思路，去聊它的底层构成。这个过程的第一个阶段——一共有三个阶段——就是预训练（pre-training）阶段，它本质上就是把互联网上的知识获取并装进这个神经网络的参数里。于是神经网络把互联网上的大量知识内化了进去。但模型真正的「性格」，其实是在监督微调（SFT）这个过程中塑造出来的。这里发生的事情是，像 OpenAI 这样的公司，会精心整理一个大规模的对话数据集，比如 100 万段跨越各种主题的对话，它们都是人类与助手之间的对话。尽管这整个过程里用到了大量的合成数据生成、大量的 LLM 辅助等等，但归根结底，这是一项由大量人类参与的人工数据整理工作。具体来说，这些人是被 OpenAI 雇佣的数据标注员，他们会学习给定的标注指南，他们的任务是为任意提示词创作出理想的助手回复。所以他们是在用「示例」教神经网络如何回应提示词。

L315那么该怎么理解这里返回的东西呢？这到底是什么？我认为，正确的理解方式是：这是神经网络在模拟 OpenAI 的一名数据标注员。就好像我把这个查询交给 OpenAI 的一名数据标注员，这名标注员先读完 OpenAI 所有的标注指南，然后花两个小时为这个查询写下一份理想的助手回复，再交给我。当然，我们其实并没有真的这么做，对吧？因为我们并没有等两个小时。所以我们这里拿到的，是神经网络对那个过程的模拟。而且我们要记住，这些神经网络并不像人类大脑那样运作，它们是不同的。对它们来说容易或困难的事，和对人类来说容易或困难的事并不一样。所以我们拿到的确实只是一个模拟。我在这里展示的是一个词元流，而它本质上是一个神经网络，中间有一大堆激活值和神经元。这是一个固定的数学表达式，它把来自词元的输入和模型的参数混合在一起，混合之后输出序列里的下一个词元。但这是每一个词元都会发生的、有限量的计算。所以这是对人的一种有损模拟，它在这种意义上是被限制住的。所以不管人类写的是什么，语言模型基本上都是在词元这一层去模仿，对序列中的每一个词元只进行这种特定的计算。

L317我们还看到，正是因为这些以及认知上的差异，模型会在很多方面出问题，你使用它们时必须非常小心。比如我们看到，它们会出现幻觉。而且我们还会有一种「瑞士奶酪」式的能力模型，奶酪里是有洞的——有时候模型会莫名其妙地做出很蠢的事情。所以即便它们能做出很多神奇的东西，有时候它们就是不行。也许是你没给它们足够的词元去思考，也许它们会直接瞎编，因为它们的心算崩了。也许它们突然数不出字母的数量，也许它们没法告诉你 9.11 比 9.9 小，看起来挺蠢的。所以这是一种「瑞士奶酪式」的能力，我们必须对此保持谨慎。我们看到造成这些的原因。但归根结底，这就是我们对返回内容的理解方式——再说一次，它是神经网络对一名遵循 OpenAI 标注指南的人类数据标注员的模拟。这就是我们拿回来的东西。

概念索引

复习时可以先扫这一页，把术语和直觉对上，再回到对应章节读原文。

LLM
Large Language Model，大语言模型；以词元序列为输入和输出的神经网络模型。
心智模型
帮助你预测系统行为的一组简化理解，比如“它在预测下一个词元”。
锋利边缘
看起来很强但容易误用的边界条件，如幻觉、心算错误、过度自信。
FineWeb
Hugging Face 构建的高质量网页文本数据集，视频中作为生产级数据处理的代表例子。
Common Crawl
从 2007 年起抓取互联网网页的组织，很多训练语料的原始来源之一。
URL 过滤
用黑名单等规则剔除恶意、垃圾、营销、成人等不想纳入的数据来源。
文本抽取
从网页 HTML 中提取正文，丢掉导航、样式、脚本等非正文内容。
PII 移除
移除个人身份信息，如地址、社会安全号码等。
UTF-8
把文本编码成计算机可存储的比特序列的一种标准。
字节
8 个比特组成的单位，共有 256 种可能取值。
BPE
Byte Pair Encoding，字节对编码；不断合并常见相邻符号，得到更大的词表和更短的序列。
token
词元；模型实际处理的最小符号单元，可以是字、词、空格加词、标点或更奇怪的片段。
词表
模型允许出现的所有 token 集合。GPT-4 相关分词器约有 10 万个符号。
上下文
当前喂给模型的一段 token 序列，长度有最大限制。
标签
训练数据中真实出现的下一个 token。
参数/权重
神经网络里可被训练调整的数字，可理解成大量旋钮。
损失
衡量预测与真实 token 不一致程度的指标，训练目标是让它下降。
推理
模型训练完后，用固定参数生成输出的过程。
采样
根据概率分布随机选出下一个 token，因此同一输入可得到不同答案。
GPT-2
OpenAI 2019 年发布的语言模型，视频中用来展示训练与推理的具体过程。
GPU
图形处理器，擅长大规模并行矩阵运算。
H100
NVIDIA 的高端数据中心 GPU，视频中用作训练算力例子。
节点
一台含多块 GPU 的训练机器；多个节点可组成更大的训练集群。
基座模型
只经过预训练、尚未被系统训练成对话助手的模型。
有损压缩
参数保留了互联网文本的整体统计印象，但不是逐字可查的数据库。
幻觉
模型在缺乏可靠知识时生成看似合理但不真实的内容。
少样本提示
在提示词中给几个输入输出例子，让模型在上下文里学会模式。
上下文学习
模型在当前上下文中识别模式并临时按模式续写的能力。
后训练
基座模型之后的训练阶段，用来塑造助手行为、推理习惯和安全边界。
SFT
Supervised Fine-Tuning，监督微调；用理想对话回复继续训练模型。
标注指南
告诉人类标注员什么回答更 helpful、truthful、harmless 的规则文档。
特殊词元
用于标记对话结构的 token，如 im_start、im_end、user、assistant。
对话协议
把多轮对话编码成一维 token 序列的一套格式规则。
工具调用
模型输出特殊 token 或请求，让外部搜索、代码解释器等工具补充信息或执行计算。
上下文窗口
模型当前可直接访问的 token 范围，可视为工作记忆。
系统消息
隐藏在对话最前面的指令，用来设定身份、规则和行为边界。
思维链
把推理步骤展开成一串中间 token，让计算分布在多个生成步骤上。
瑞士奶酪模型
模型能力有洞：整体强大，但存在随机、局部、反直觉的失败点。
强化学习
通过试错和奖励信号改进行为的训练方式。
可验证领域
答案能被明确检查的任务，如数学题、代码运行结果。
奖励
告诉模型某个候选解法好或坏的信号。
思考模型
经过更强推理训练、会在回答前生成较长推理过程的模型。
第 37 手
AlphaGo 对李世石的著名一步，代表 RL 发现非人类常规策略的能力。
不可验证领域
没有明确标准答案、需要人类主观判断质量的任务。
RLHF
Reinforcement Learning from Human Feedback，基于人类反馈的强化学习。
奖励模型
学习模仿人类偏好排序的独立模型，用来给候选回答打分。
判别器-生成器差距
判断好坏通常比亲自生成高质量作品更容易。
对抗样本
专门钻模型漏洞、让模型给出异常高分的输入或输出。
多模态
模型同时处理文本、音频、图像等不同信息形式。
智能体
能持续执行多步任务、汇报进展并与工具互动的模型系统。
测试时训练
让模型在部署后的任务过程中更新自身能力的研究方向，区别于只扩展上下文。
开放权重
模型参数可被下载、托管和再使用的发布方式。
蒸馏模型
把大模型能力压缩到更小模型中的模型，便于本地运行。
有损模拟
模型近似模仿人类写回复的过程，但受 token、参数和有限计算限制。
固定数学函数
部署后的模型参数固定；每个 token 的输出由同一个网络前向计算得到。
工具心态
把模型当作协作者和加速器，而不是无条件可信的权威。
